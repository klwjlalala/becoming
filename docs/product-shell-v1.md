# 产品化 V1：本地优先桌面端交互与服务架构基线

状态：产品化阶段设计稿，待审查；不是已实现功能  
依赖：PR #1–#7 的核心 Agent、长期记忆、自我探索/引导、成长服务和动态个人理解  
目标：把当前 CLI 研究原型变成可持续日常使用的个人 AI 伙伴，不继续扩张认知算法。

## 1. 产品定位与验收原则

Becoming 首先是一个长期、自然、可信赖的 AI 伙伴，帮助用户理解自己、梳理困惑、在迷茫时获得有依据的分析和建议。

产品优先级：

1. 自然交流和长期关系连续性。
2. 逐渐形成、能够修正的个人理解。
3. 用户明确需要时提供成长目标、行动与复盘工具。
4. 记忆和成长数据的透明管理与用户控制。

产品不以任务完成率、人格评分、连续打卡、画像完整度或 AI 主动干预次数衡量价值。

核心交互约束：

- 默认进入对话，不先展示仪表盘、人格报告或任务列表。
- 不主动向用户播报“画像更新”；个人理解只在当前交流确实相关时自然体现。
- 不把每次倾诉变成计划，不把愿望自动转成任务。
- 成长工具只在用户明确需要时出现；任何持久化变更继续使用预览和明确确认。
- 用户对自己的最终解释权高于模型推断；允许纠正、暂停、删除和导出。
- 记忆管理入口应可发现，但不占据日常聊天主界面。

## 2. V1 产品范围

### P0：首次启动与模型配置

- 首次启动进入简洁配置向导：服务商/兼容接口、Base URL、API Key、模型名称。
- 提供“测试连接”，明确区分配置缺失、鉴权失败、网络失败和模型不可用。
- 连接成功后进入主对话；允许在设置中修改配置。
- API Key 不写入 renderer 的 localStorage、普通配置文件或日志。桌面端使用操作系统安全存储；Python 服务只在运行时接收所需凭据。
- 不预置任何真实 API Key，不强制绑定单一供应商。

### P0：主对话

- 对话是首页和主要工作区。
- 支持新建对话、历史对话列表、切换对话、重命名/归档和删除。
- 当前对话有独立的近期上下文；长期记忆和个人理解属于用户级上下文，可跨对话使用，但必须按当前问题相关性检索。
- 发送中、模型响应失败、重试、取消（若底层请求支持）等状态清晰可见。
- 不显示内部 Evidence/Claim/Revision 处理流水线；不在每轮结束后弹出“已更新画像”提示。
- 对话内容以自然文本为主；必要时展示成长变更预览卡片和明确的确认/取消操作。

### P1：成长空间

- 作为次级入口，不作为首页。
- 查看成长目标、行动和复盘；支持筛选、分页、暂停/完成、编辑和删除。
- 对话中提出的变更仍由 GrowthStore 生成真实状态预览，用户确认后才写入。
- 普通聊天、愿望表达和建议讨论不自动创建成长记录。
- 不做提醒、打卡、积分、连续天数或排行榜。

### P1：记忆与隐私管理

设置中的独立区域，至少包括：

- 查看长期记忆原话、来源对话、记录时间、当前状态。
- 查看个人理解命题、支持/反向/限定证据、版本历史及其置信支持等级。
- 用户可以纠正、拒绝或删除理解；拒绝后不应继续作为当前建议依据。
- 支持删除单条记忆、删除单个对话及清除全部个人数据。
- 提供数据导出，至少包含对话、长期记忆、个人理解及成长数据。
- 删除界面必须说明各类数据影响范围；不能只删除主表而遗留可继续召回的副本。

### P2：后续再做

- 多设备同步、账号体系、云端数据库、多用户共享。
- 主动提醒、日程推送、自动打卡、后台自主行动。
- 社交、社区、公开画像、人格测评。
- 复杂数据看板、关系分数、自动心理诊断。
- 向量检索/语义重排等没有真实失败样本支撑的算法扩展。

## 3. 关键页面与交互结构

### 3.1 主窗口

- 左侧窄导航：对话、成长、设置。
- 对话页占据主要空间；历史列表可收纳/展开。
- 主聊天区不常驻“AI 对你的画像”侧栏，不放 KPI、成长分数或任务仪表盘。
- 顶部只展示当前对话标题和模型/连接状态；底部输入区支持多行输入。
- 视觉方向：安静、克制、耐看，优先护眼的暗色主题；减少卡片堆叠和装饰性数据。

### 3.2 对话中的成长变更

- 模型明确提出成长工具请求后，展示由本地数据库生成的预览。
- 预览清楚说明新增/修改/删除对象及影响范围。
- 用户确认后显示真实执行结果；取消或发起新对话时使旧提案失效。
- 不将模型文本中的“我已保存”当作实际成功证据。

### 3.3 记忆管理

- 不在每轮对话中展示理解更新。
- 用户主动进入设置时，能够检查 AI 依据哪些原话形成某项理解。
- 显示“用户原话 / AI 当前理解 / 适用范围 / 证据 / 版本”之间的区别。
- 允许用户直接修正，不要求用户证明 AI 为什么错。
- 用户删除来源对话时，相关证据必须级联清理；若 Claim 不再有有效证据，不得继续召回。

## 4. 技术架构建议

### 4.1 分层

- Renderer：Electron + Vue 3 + Vite + Pinia，负责界面与本地交互状态。
- Electron Main：窗口生命周期、系统安全存储、Python 子进程生命周期、文件选择/导出。
- Python Core：继续复用当前 `becoming` 包，负责 Agent、模型适配、SQLite、长期记忆、个人理解和成长工具。
- IPC：Renderer 只能调用 Main 暴露的窄接口；不允许 renderer 任意访问 Node 或文件系统。

### 4.2 Python 服务通信

建议先采用 Electron Main 启动单个长期运行的 Python sidecar，通过 stdin/stdout JSONL 请求/响应通信，而不是开放固定 localhost 端口。

初始协议建议：

- 请求：`{id, method, params}`
- 响应：`{id, ok, result}` 或 `{id, ok:false, error}`
- 日志只写 stderr；stdout 只输出协议 JSONL。
- 所有请求带唯一 id；启动握手、协议版本和服务退出状态明确。
- 第一版先支持完整回复，不强制实现 token streaming；底层模型接口仍是同步 complete。
- 后续若需要流式输出，再扩展为带 request id 的增量事件，不另建第二套 Agent。

该方案的优势是复用 Python 领域逻辑、避免固定端口与浏览器跨域暴露；代价是需要处理子进程崩溃、重启、协议版本和 Python 运行时打包。

### 4.3 建议的服务方法

- `health` / `get_app_state`
- `test_model_connection` / `update_model_config`
- `list_conversations` / `create_conversation` / `rename_conversation` / `archive_conversation` / `delete_conversation`
- `get_history` / `send_message`
- `confirm_growth_change` / `cancel_growth_change`
- `list_long_memories` / `forget_long_memory`
- `list_understanding_claims` / `get_understanding_history` / `correct_understanding` / `reject_understanding`
- `export_user_data` / `clear_user_data`

接口只作为产品边界建议，实施时按真实领域对象收敛，不为每个 UI 控件制造一个后端接口。

## 5. 需要在产品接入前解决的结构性事项

以下属于产品可用性的必要工作，不要求在当前 PR #7 中追加：

1. **对话会话模型**：当前 turns 表是单一连续历史，没有 conversation_id。产品需要新增 conversations 表和数据库迁移；近期历史按当前会话读取，长期记忆/个人理解仍可跨会话检索。
2. **回复与记忆更新解耦**：当前长期记忆提取和个人理解批处理在 Agent.reply() 尾部同步执行，可能让用户等待额外模型调用。产品服务应先返回主回复，再由同一 Python 服务的持久化队列处理后置更新；失败可恢复、状态可观测，不能丢弃用户回复。
3. **统一数据删除/导出**：当前成长数据和对话数据位于两个 SQLite 文件，/clear 不会清理成长库，也无法保证删除对话/成长数据在历史文本中的副本。产品需提供统一的导出和“清除全部本地数据”流程，并验证两库状态；说明逻辑删除、备份及模型服务副本的边界。
4. **配置安全**：从环境变量研究模式过渡到桌面端安全配置；密钥不能被 renderer 读取或进入日志。
5. **数据库迁移与恢复**：增加 schema version、启动迁移、迁移失败保护和本地备份/恢复策略。不得在升级时静默丢失既有 CLI 数据。

以上五项是进入可日常使用的桌面 MVP 前的结构性事项。暂不要求实现多用户、云同步、加密同步协议或复杂后台调度平台。

## 6. 建议实施顺序

1. 对话会话模型与 SQLite 迁移；现有 CLI 默认行为保持兼容。
2. Python JSONL 服务入口与协议测试；覆盖启动、请求关联、错误隔离、重启和退出。
3. 将回复生成与后置记忆处理分离，建立持久化、可恢复的后台任务队列。
4. Electron + Vue 3 最小桌面壳：首次配置、测试连接、主对话、历史列表。
5. 接入成长空间、记忆管理和统一数据导出/删除。
6. 做端到端功能测试与有限真实模型体验测试；再决定是否扩大 UI 或新增功能。

## 7. V1 验收标准

- 新用户可以配置任意兼容服务并验证连接，不需要编辑 .env。
- 用户可以开始对话、创建多个会话、切换历史；重启后会话仍在。
- 当前会话的近期历史不会串到其他会话；用户级记忆能够跨会话按相关性使用。
- 主回复不因长期记忆提取/个人理解整理而被不必要地阻塞；应用重启后未完成的更新任务可恢复。
- 成长工具只有在明确请求时使用；修改/删除必须由用户确认。
- 用户能够查看记忆来源、纠正或删除理解，并导出/清除全部本地数据。
- 删除会话后，来源证据与无证据命题不再参与召回；清除全部数据后两个 SQLite 数据库均无残留业务记录。
- API Key 不出现在 renderer、日志、Git、导出文件或对话历史中。
- 所有核心流程有离线自动化测试；至少完成一轮虚构数据的真实模型端到端体验评估。

## 8. 明确不作为 V1 阻塞项

- token 级流式输出（先用清晰的等待状态）。
- 向量数据库和语义重排。
- 复杂的多主题标签、自动画像编辑器。
- 云同步、多用户、团队协作。
- 全量自动化质量评分或 LLM 裁判。
- 任何没有真实用户场景或复现失败案例支撑的局部算法优化。

## 9. 决策状态

当前建议基线为本地优先桌面应用：Electron + Vue 3 前端，复用 Python 核心，不重写 Agent 业务逻辑。先完成会话模型、服务边界和回复/后台记忆处理解耦，再做 UI。若后续用户实际使用证明某个页面或机制没有价值，再删减，而不是预先堆叠更多模块。
