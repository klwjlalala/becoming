# AI 好友综合长会话评测

## 目的

验证真实产品运行方式下，近期对话、长期记忆与动态个人理解能否在同一段长会话中协同工作。该评测补充既有的单模块纵向评测，不替代原有专项测试。

## 运行配置

- 使用 evaluation/personal_understanding_cases.json 中的 30 轮虚构用户时间线（2024–2026）。
- 所有轮次写入同一个长期会话，按 fixture 日期设置 turns.created_at。
- Agent 近期历史窗口为 12 轮，与当前 Web Agent 默认配置一致。
- 同时启用 LongMemory 与 PersonalUnderstanding；不启用 GrowthTools，避免把本轮重点扩展到成长工具行为。
- 每 5 轮排空一次后台任务队列，使普通个人理解更新可以批处理；明确纠正仍保留即时优先级。
- 使用独立内存 SQLite，不读写真实用户数据或本地数据库。
- 在 30 轮综合总结之后，再用 historyTurns=0 的独立 Agent 发起一次早期偏好回忆探针，单独核验长期记忆召回。
- 以相同的最后 12 轮历史、但关闭记忆和个人理解的基线 Agent 回答同一个综合问题，作为定性参照。

## Fixture 分类说明

2025-08-19 的“可能不想再做这个小工具了，最近维护它有点消耗”不归类为短暂情绪：它针对一个持续项目，表达了带有不确定性的意向变化，并说明了具体原因，因此作为带时间语境的项目状态证据保留。2025-07-03 的“今天有点烦，什么都不想做，明天应该就好了”仍是 no-write，用来验证短暂情绪不会被固化为长期偏好。

## 验证内容

### 自动结构性检查

1. 所有 30 轮真实模型回复成功完成，且记忆/个人理解检索没有运行错误。
2. fixture 标记为 no_write 的第三方叙述、假设、短暂情绪、倾听请求、普通技术问题和综合提问，不产生长期记忆或个人理解 Evidence。
3. 明确纠正 AI 误解的轮次产生可追溯的个人理解 Evidence。
4. 后台记忆提取与个人理解更新队列完成，无遗留失败任务。
5. 最后一轮综合提问实际召回个人理解 Claim。
6. 第三方话题、短暂情绪和明确倾诉请求，不会向回复上下文注入不相关的长期记忆。
7. 30 轮之后，historyTurns=0 的探针仍能从长期记忆召回早期“比起职位头衔，更在意自主安排时间”的原始陈述。

记忆提取中，模型提出已有 Key 但未提供有效替换关系的候选应被拒绝并记为 rejected，不应反复重试并让整个后台任务失败；旧记忆必须保持不变。

这些断言验证数据流和结构，不自动判断回复是否真正理解用户。

### 人工质量审查

- 连续交流是否自然，是否有明显模板化、重复总结或机械追问。
- 是否能承接近期上下文，同时不过度依赖最近 12 轮。
- 是否在用户要求倾听时停止给方案，在普通技术问题时直接回答。
- 是否正确区分用户本人、第三方、假设和短暂情绪。
- 用户重新解释社交偏好时，是否细化而非简单反转旧标签。
- 用户明确纠正创业目标时，是否接受纠正，不再把创业当作终极目标。
- 是否同时保留自主时间、选择权与稳定现金流之间的真实张力。
- 是否把山顶经历作为具体经历，而不是据此推断固定人格或人生使命。
- 是否在最终总结中区分用户明确表达、跨轮观察和仍不确定的解释。
- 早期偏好回忆是否准确、克制，并且不编造来源。
- 与无记忆/个人理解基线相比，新增上下文是否真正改善回答，而不是仅增加冗长内容。

## 预算与执行

GitHub Actions suite 名称为 long-session。使用仓库现有 BECOMING_BASE_URL、BECOMING_API_KEY、BECOMING_MODEL Secrets。

真实模型调用硬上限为 100 次；按当前流程预估约 68 次，实际数量会随后台批次与模型校验重试变化。模型调用失败不会自动无限重试。

报告包含逐轮用户输入、模型回复、召回 ID、记忆与 Claim 版本历史、no-write 检查、基线回复和模型调用 trace，作为 GitHub Actions Artifact 上传，保留 14 天。

报告不包含 API Key 或 Authorization Header。所有输入均为合成数据。工作流成功只表示评测流程和结构性断言通过；语义质量必须人工阅读逐轮对话后判断，不使用同一个模型自评。

## 当前限制

这是一个固定的合成 30 轮场景，不代表所有真实用户或所有话题。模型随机性会影响输出；单次通过不能证明长期关系已经成立。后续应根据人工审查发现的问题，增加针对性反例，而不是盲目增加轮数或扩大测试预算。


## 2026-11-28 真实模型评测结果

<badge>GitHub Actions</badge> [Run #46099466322](https://github.com/klwjlalala/becoming/actions/runs/46099466322)

- 结果：通过；30 轮同一长期会话；近期历史窗口 12 轮；同时启用长期记忆与动态个人理解；关闭成长工具。
- 模型调用：70 次，硬上限 100 次。
- 持久化结果：15 条活跃长期记忆、10 条活跃个人理解 Claim。
- no-write：7 个场景均未产生长期记忆或个人理解 Evidence。
- 检索抑制：第三方话题、短暂情绪、明确倾诉请求 3 项全部通过。
- 纠正处理：明确纠正轮次产生 1 条可追溯 Evidence；旧 Claim 保留历史版本，当前 Claim 修订为“创业只是可选方式，不是必须目标”。
- 后台处理：60 个任务全部 done；无 pending、running 或 failed。
- 跨轮回忆：30 轮之后关闭近期历史窗口（historyTurns=0），仍准确召回早期“比起职位头衔，更在意自主安排时间”的原始记忆。

### 人工审查结论

- 对话连续性良好：能结合稳定工作、家庭固定支出、自主时间、项目维护负担等不同时间的信息。
- 对用户纠正的响应良好：承认曾把“考虑过独立开发”过度归纳为“想创业”，随后修订理解，没有继续把创业当成目标。
- 个人理解能够保留变化：社交偏好从“不喜欢社交”细化为“不喜欢应酬式社交，但喜欢围绕共同兴趣深入交流”；项目意向从“尝试独立开发”演变为“当前不把产品当成必须完成的目标”。
- 对山顶经历保留为意义尚不明确的个人事件，没有把一次感动直接推断成固定人格或人生使命。
- 技术问题话题切换正常；倾听请求没有给出行动方案。
- 长期记忆与个人理解的检索抑制现在保持一致，不再向第三方、短暂情绪和倾诉请求注入不相关的旧记忆。

### 基线比较与限制

同样使用最后 12 轮历史、关闭长期记忆和个人理解的基线回答为 661 个字符；综合模式回答为 489 个字符。两者都抓住了自主时间、稳定现金流、兴趣与创业之间的主要取舍。综合模式更简洁，但这次对比没有证明它在语义质量上显著优于基线。

因此，本轮通过证明的是：长期信息可以持久化、修订、在长会话后召回，且不会明显污染第三方/短暂情绪/倾诉场景。它还不能证明真实用户使用数周后一定会形成更好的长期关系；这需要真实使用和人工反馈。

### 执行中发现并修复的问题

1. 将具体项目维护负担导致的阶段性意向变化，从“短暂情绪”重新分类为有时间语境的项目状态证据；普通短暂情绪仍保持 no-write。
2. 长期记忆检索统一使用个人理解模块的第三方、短暂情绪和倾听抑制规则。
3. 模型提出已有 Key、但未给出有效 replaces 的记忆候选时，拒绝该候选并保留旧记忆，不再反复重试导致整个后台任务失败。

执行过程共发生三次真实评测尝试，模型调用数分别为 69、35、70；前两次分别暴露评测分类和记忆冲突处理问题，最终一次完成全部 30 轮及所有结构性断言。上述调用次数不是 Token 数，精确 Token 用量未由报告提供。
