# 动态个人理解模型 V1 技术设计基线

状态：V1 首轮实现基线；代码已接入独立分支，真实模型效果仍待 Live 验收  
适用分支：feat/dynamic-personal-understanding-v1  
依赖：当前 Becoming 核心 Agent、SQLite 对话存储、可选长期记忆与成长服务

## 1. 目标与边界

V1 要验证的不是“生成一份完整用户画像”，而是让 Agent 能够从跨时间的用户表达中形成有证据的理解，在新证据出现时正确修订，并在当前对话确实相关时自然使用这些理解。

用户已确认的产品选择：

1. 自主形成理解；对重要、尚不确定且会实质影响建议的认识，在自然交流中适时确认。
2. 混合更新：重要变化即时处理，普通证据延迟批处理，定期复核。
3. 不主动向用户汇报画像或变化；只在自然交流中体现理解。

V1 不把心理诊断、人格打分、关系亲密度评分或自主干预作为目标。

## 2. 架构收敛：先做 U-Model，不把三个状态都做成数据库

此前提出 U-Model、R-State、C-State 三部分。实现时应避免重复保存现有数据：

- U-Model（持久化）：本阶段真正新增的动态个人理解，包括证据、命题、版本和修订记录。
- R-State（暂不独立持久化）：当前由对话历史、长期记忆、成长工具事件和用户对 AI 的反馈提供。只有当“未完成讨论”“双方约定”等具体用例证明现有记录不足时，再增加专门结构。
- C-State（运行时临时对象）：由当前消息、近期上下文和本轮检索结果组装，不另建长期状态表。

因此 V1 的主数据链是 Evidence → Claim → Revision。关系连续性和当前情境作为输入，不复制为第二套记忆。

## 3. 核心数据对象

### 3.1 Evidence：可追溯证据

Evidence 只描述用户在某个时间表达过的内容，不把模型解释混入原话。

建议字段：

| 字段 | 含义 |
| --- | --- |
| id | 证据 ID |
| source_turn_id | 原始用户对话轮次 ID，外键关联 turns |
| quote | 从该轮用户输入中逐字截取的完整语义片段 |
| kind | direct_statement / self_interpretation / correction / experience / outcome_feedback / context |
| event_time | 用户明确提供的事件时间；未知时为空 |
| recorded_at | 系统记录时间 |
| created_at | 证据入库时间 |

约束：

- 只从 user_text 提取证据，不把助手的总结当作用户事实。
- quote 必须是源文本中的连续片段，并通过完整分句、条件、否定、转折和归属边界校验。
- 不把记录时间当成事件发生时间。
- 同一 source_turn_id + quote 幂等，不重复创建。
- 第三方观点、假设、反问、短暂情绪和普通闲聊不应自动形成长期证据。
- 不自动推断敏感属性、医学诊断或第三方隐私；凭据类内容直接拒绝。

### 3.2 Claim：个人理解命题

Claim 是 AI 当前对用户形成的一项可修正认识。它不是客观人格标签，也不能脱离证据单独存在。

建议使用稳定的 claim_id + 不可覆盖的版本记录：

| 字段 | 含义 |
| --- | --- |
| claim_id | 同一理解主题的稳定 ID |
| version | 当前版本号 |
| content | 一句范围明确、不过度绝对化的理解 |
| dimension | values / motivation / needs / goals / patterns / cognition / self_concept / constraints / tensions |
| basis | explicit_statement / self_interpretation / ai_inference / repeated_expression / reported_outcome |
| scope_json | 适用情境与条件 |
| temporal_scope | 时间限定；未知时明确写 unknown，不猜测 |
| support_level | low / medium / high，表示证据支持程度，不表示客观真理 |
| user_validation | unconfirmed / confirmed / rejected |
| status | active / disputed / superseded / expired / rejected |
| created_at / updated_at | 创建与更新记录 |

重要区分：

- “用户明确表达过 X”是关于表达的事实。
- “用户长期重视 X”是可能需要多条证据支持的理解。
- 用户明确认可 AI 的某种概括，才将 user_validation 置为 confirmed。
- 用户没有反驳，不代表确认。
- AI 推断不能伪装成用户原话或用户确认。

### 3.3 ClaimVersion：版本历史

每次实质修订都创建新版本，保留旧内容、旧证据关系和修订原因。版本内容不做原位覆盖；生命周期状态可以从 active 转为 superseded / disputed / expired，并记录对应 Revision。

建议字段：

- id、claim_id、version
- content、dimension、basis、scope_json、temporal_scope
- support_level、user_validation、status
- revision_reason、created_at

### 3.4 ClaimEvidence：命题与证据关系

采用多对多关系，不把一条证据强行绑定为唯一结论。

relation 取值：

- support：支持该命题
- counter：与该命题冲突或构成反证
- qualifies：为该命题增加条件或适用范围

同一命题可以同时存在支持证据和反向证据。出现冲突不意味着必须选出一个“正确人格”。

### 3.5 Revision：修订审计

建议字段：

- id、claim_id
- from_version_id、to_version_id（关联版本记录）
- operation
- reason
- created_at
- revision_evidence：独立关联表，保存本次修订依据的 evidence_id；来源删除时级联清理

V1 操作：

| 操作 | 含义 |
| --- | --- |
| CREATE | 创建新命题 |
| REINFORCE | 新证据支持原命题，更新证据集合 |
| REFINE | 在原主题内细化表达或适用范围 |
| SUPERSEDE | 用户明确改变或纠正同一主题的认识 |
| DISPUTE | 存在实质冲突，但目前无法解释 |
| EXPIRE | 时间性认识不再适用 |
| CONFIRM | 用户明确认可某项 AI 概括 |
| REJECT | 用户明确否定某项 AI 概括 |

“拆分情境”优先通过新增带有不同 scope 的命题实现；旧命题保留并在必要时标记 disputed，不强行合并。

### 3.6 PendingConfirmation：待确认事项

仅在以下条件同时满足时创建：

1. 某条 AI 推断会实质影响当前建议或长期理解。
2. 证据不足以安全地当成已确认认识。
3. 助手在自然回复中确实向用户提出了与该命题直接相关的确认问题。

建议字段：claim_id、claim_version、source_turn_id、question、status、expires_after_turn_id、created_at。

问题文本必须能在对应 assistant_text 中找到；不能由提取模型虚构“助手问过的问题”。待确认事项只等待紧接着的用户回应；若用户转移话题或回应不明确，则过期，不反复追问。只有明确肯定或否定才更新 user_validation。

## 4. SQLite 表关系

建议新增以下表，均与现有对话数据库共用连接：

| 表 | 用途 |
| --- | --- |
| understanding_evidence | 原始证据与来源轮次 |
| understanding_claims | 稳定命题 ID 与当前版本/状态 |
| understanding_claim_versions | 每个命题的版本内容 |
| understanding_claim_evidence | 版本与支持/反向/限定证据的关联 |
| understanding_revisions | 每次修订的审计记录 |
| understanding_revision_evidence | 修订与来源证据的关联 |
| understanding_pending_confirmations | 自然对话中等待用户确认的事项 |
| understanding_jobs | 延迟提取、即时修订和周期复核队列 |

所有 source_turn_id 都应外键关联 turns 并级联删除。删除来源证据后，不允许把无证据的命题继续作为当前理解使用；删除全部对话时，应一并清除关联命题、版本、修订与待确认项。长期记忆表不被本模块修改，二者只共享原始对话来源。

## 5. Understanding Update Engine

### 5.1 单轮流程

1. 读取本轮 user_text、assistant_text、相关活跃 Claim 和待确认事项。
2. 证据提取：模型给出候选 Evidence，必须逐字引用当前用户原话。
3. 关联判断：将新证据与已有 Claim 比较，判断支持、补充、限定、纠正、变化、冲突或无关。
4. 生成操作提案：模型只能引用输入中存在的 claim_id、version 和 evidence local_ref。
5. 程序校验：校验 JSON、字段枚举、来源轮次、原话边界、ID、版本、操作合法性和凭据过滤。
6. 事务写入：证据、版本、关联和 Revision 在同一事务内提交；任何非法引用不得造成部分越权更新。
7. 记录结构化事件：写入、拒绝、冲突、重试、召回等均可被测试观察。

模型只提出操作建议，数据库层决定是否允许执行。模型不得直接指定 support_level、当前版本号或任意 SQL。

### 5.2 更新时机

| 类型 | 触发 | 处理 |
| --- | --- | --- |
| 即时 | 明确纠正、明确改变重要目标、重新解释重要经历、用户明确指出 AI 误解 | 本轮回复完成后立即分析并提交；失败则进入重试队列 |
| 延迟批处理 | 普通偏好、经历、重复表达、一般自我认识 | 先持久化 job，不阻塞本轮回复；最多 5 个轮次合并为一次模型分析 |
| 周期触发 | 每累计 20 个对话轮次 | 当前 V1 仅触发一次积压队列处理，不执行独立的全量 Claim 复核；跨 Claim 周期复核暂缓 |

“即时”是指重要变化不等待下一批次；当前 Agent 在生成并保存回复后同步执行一次模型更新调用。重要触发目前由一组明确纠正/改变意图的关键词规则识别，未命中时会进入普通队列。普通证据在积累到 5 条或第 20 轮触发点时同步处理；因此第 5 条到达时可能增加当前 reply() 的尾延迟。CLI 退出时调用 flush。当前原型没有独立常驻调度服务，也没有真正的异步后台任务；GUI/服务端后续应将 process_pending 放入 worker。

队列要求：job_key 幂等、状态 pending/running/done/failed、有限重试（flush 最多重试至 3 次）、失败可见、来源轮次删除时级联清理。批处理失败不得部分提交该批命题。

### 5.3 冲突处理规则

| 新证据情况 | 处理 |
| --- | --- |
| 同一认识的独立支持证据 | REINFORCE |
| 原命题需要增加限定 | REFINE |
| 用户明确说以前表达错误 | SUPERSEDE，并保留旧版本 |
| 用户明确表示想法随时间改变 | SUPERSEDE，旧版本作为历史认识 |
| 不同情境下分别成立 | 新建带 scope 的命题，不强行覆盖 |
| 证据互相冲突且原因不明 | DISPUTE，保留双方证据 |
| 用户明确否定 AI 的概括 | REJECT，不再作为当前建议依据 |
| 短暂状态或普通话题 | 不创建长期 Claim |

用户当前表达优先决定当前对话与当前行动，但不自动抹掉长期价值观。一次情绪表达不能单独推翻长期命题；需要判断它是短期状态、情境变化还是稳定认识改变。

### 5.4 Support Level 计算

support_level 不由模型自评，而由程序根据证据关系、独立来源轮次、证据跨度、反证数量和用户确认状态计算。

- high：至少 3 个独立来源轮次分布在不同记录日期，且没有反证；或用户明确确认。
- medium：至少 2 个独立来源轮次支持，且没有反证。
- low：单条证据、证据含糊或存在反证。

即使 high，也只代表“当前证据支持较强”，不代表对用户的客观定论。V1 先使用离散等级，不使用 0.87 等虚假精确数值。

## 6. Interaction Strategy Engine

V1 不额外增加一次独立的策略模型调用。InteractionStrategy 负责检索、过滤和组装指导，由本轮主模型在同一次回复生成中选择交流方式。

### 6.1 检索

- 默认只检索 active 与必要的 disputed 命题。
- superseded / expired / rejected 不参与当前建议；只有用户明确回顾历史时才允许召回。
- 当前实现使用中文二元词/英文词法重叠，并对“真正想要、人生、价值观、迷茫、取舍”等反思类提问提供有限的维度召回兜底。
- 最多注入 5 条命题，序列化上下文上限 6000 字符；超限时丢弃排序靠后的命题。
- 当前不额外调用模型做语义筛选；无明确词法或反思意图时不注入。
- 不把完整用户画像或所有历史原话塞入每轮 Prompt。
- 记录候选、入选、实际注入的 claim_id 与理由，供测试检查误用。

### 6.2 交流策略

策略模式：NORMAL、LISTEN、EXPLORE、REFLECT、ADVISE。

系统指导：

- 普通闲聊正常交流，不刻意引用历史。
- 用户倾诉时先倾听，不把倾诉自动转换为计划或任务。
- 用户希望理解自己时，通过有价值的追问帮助探索。
- 只有当历史模式与当前问题确实相关时，才自然联系过去。
- 不确定的推断使用试探性表达，不把它说成事实。
- 重要建议依赖未确认认识时，才自然询问用户是否仍然适用。
- 不主动汇报“画像更新”，不展示分析流水线。
- 当前明确表达优先；旧理解只能作为背景，不得压过用户当前决定。
- 不为了展示记忆能力而反复提及历史。

## 7. 与现有模块的边界

- LongMemory：保存和召回用户明确表达的事实、经历、偏好；本模块不改写其表、提示词或提取流程。
- PersonalUnderstanding：解释多条证据之间的关系，形成可修订命题。
- GrowthStore：保存用户确认的成长目标、行动和复盘；本模块可以将其作为关系上下文，但不能擅自创建、修改或把目标当成用户的稳定价值观。
- Agent：可选启用个人理解检索和回复后更新；默认关闭，未启用时调用次数和行为与现有版本一致。
- R-State/C-State：V1 复用已有对话与本轮上下文，不另建重复持久化模型。

## 8. 隐私、纠正与删除

- 只处理当前用户自己的表达，不把第三方观点归到用户身上。
- 不自动推断敏感属性、心理/医学诊断或身份类别。
- 证据必须有原始来源；任何 Claim 都必须至少有一条有效证据。
- 用户明确纠正时优先修订，不要求用户为 AI 的错误重复证明。
- 删除来源对话时级联删除其 Evidence；没有剩余有效证据的 Claim 不得继续召回。
- /clear 的级联删除边界应覆盖本模块数据。
- V1 仍是单用户本地 SQLite 原型；SQLite 未加密，逻辑删除不等于物理安全擦除。
- 凭据与少量敏感关键词使用规则拦截，并由模型提示词限制；这不是完整的敏感信息识别或隐私安全保证，不应存储高敏信息。

## 9. 纵向评测设计

主测试使用一个虚构用户的 30 轮连续经历，覆盖：

- 长期价值与现实约束并存；
- 初始自我描述后来被重新解释；
- 不同情境下看似矛盾的表达；
- 对 AI 既有理解的明确纠正；
- 目标随时间变化但历史不被抹除；
- 第三方观点、假设、短暂情绪和普通技术问题；
- 倾听、探索、建议和普通闲聊；
- 最后一轮综合询问“我真正想要什么、有哪些取舍、哪些认识改变”。

数据文件：evaluation/personal_understanding_cases.json。预期证据和人工评审标准只供评测端使用，不得注入被测 Agent。

对照方式：动态理解组顺序处理 30 轮；最终问题使用相同近期历史窗口，另运行不启用 PersonalUnderstanding 的基线组。比较最终回复及结构化 Claim/Revision/检索轨迹。真实模型输出必须人工审查，不使用自动 LLM 裁判宣称通过。

## 10. 验收指标

### 功能验收

- 原话来源校验、越权 ID 拒绝、重复证据幂等。
- Claim 创建、强化、细化、纠正、冲突、确认、拒绝、过期。
- 版本历史完整、Revision 可追溯。
- 延迟队列批处理、失败隔离、有限重试。
- 删除来源后不召回无证据命题。
- 检索只返回相关命题，旧版本不冒充当前认识。
- 未启用模块时，原 Agent 路径不变。

### 效果验收

- 个人理解准确性与证据支持率。
- 认知变化识别率。
- 未解释矛盾的正确保留率。
- 错误旧认知沿用率。
- 用户明确纠正后的修订成功率。
- 无依据推断率。
- 历史误用率与无关注入率。
- 用户要求倾听时的策略遵循情况。
- 普通闲聊中不主动分析用户的比例。

结构性断言与人工质量判断分开报告。CI 成功只代表离线流程通过，不代表长期关系效果已验证。

## 11. V1 明确不做

- 独立的关系亲密度或信任度分数。
- 心理类型、人格测验和医学诊断。
- 观察用户设备或外部行为。
- 向量数据库、知识图谱或复杂本体。
- 常驻自主思考循环和主动推送。
- 自动制定成长计划或修改成长工具数据。
- 多用户、云同步、加密和正式隐私合规产品化。

## 12. 实施顺序

1. [已实现] Evidence / Claim / ClaimVersion / Revision 存储、来源外键与级联清理。
2. [已实现] Update Engine、原话校验、冲突处理、确认与批处理队列。
3. [已实现] 有界检索、上下文约束与 Agent/CLI 可选集成。
4. [待执行] 真实模型显式集成测试及 30 轮纵向运行、人工审查。
5. [后续] 根据失败案例决定是否增加真正的周期复核、后台 worker、语义检索或 R-State。
