# 两类测试（V0.2）

分类依据是测试目标与是否预先指定能力，不是是否调用真实大模型。

## 1. 功能测试：能力可用性、流程与边界

目标：验证实现的每项能力能够正常使用，执行链路走通，错误与边界得到处理。不以模型自主选择能力或回答质量作为验收目标。

### 1.1 确定性工程测试（默认离线）

- 默认执行：python -m unittest discover -s tests -v
- 使用直接调用、模拟模型、Mock HTTP 响应及临时/内存 SQLite；不读取真实 API Key，不请求真实模型。
- 每次 push、PR 自动运行 Functional tests 工作流。
- 新能力必须同步增加正常路径、边界、失败恢复及回归用例。
- 对工具/Skill 等能力，除底层实现外，还须通过模拟模型响应测试 Agent 内部的注册、发现/加载、参数校验、分发、执行、结果回传和后续循环（按实际架构适用），不能只测试独立函数。

现有覆盖：

| 模块 | 主要验收 |
| --- | --- |
| Agent | 首轮上下文、历史窗口、空输入、失败不落盘、失败后可继续、存储异常 |
| SQLite | 顺序、限制、Unicode、参数化写入、原子性、清除、重开、文件隔离 |
| Model | 请求契约、响应结构、HTTP 4xx/5xx、超时、网络错误、配置校验 |
| CLI | 启动、退出、EOF、清除、重启、默认文件、异常恢复 |

### 1.2 真实模型能力集成测试（显式指令）

给真实 Agent 发送明确指定能力与测试参数的自然语言指令，通过真实模型返回及实际执行链路验证该能力能够被调用。默认不强制模型的 tool_choice，不由测试程序替 Agent 执行工具；强制调用模式可作为独立的协议测试，但不能替代显式指令集成测试。

- 文件约定：tests/live_*.py；不进入默认离线测试发现范围。
- 手动执行 Live model smoke test 工作流，或设置环境变量后运行：

      python -m unittest discover -s tests -p 'live_*.py' -v

- 现有 tests/live_smoke.py 验证真实 API、近期上下文与数据库重开闭环，属于功能测试。
- 新增每个暴露给 Agent 的 Tool、Skill 或其他可显式触发能力时，应同时添加至少一个真实模型显式调用/加载用例；如有不同执行分支，再补相应边界测试。
- 以真实的结构化事件/执行记录与状态变化断言，而不是仅匹配回复中的工具名称。记录能力 ID、参数、执行结果或错误、返回给模型的结果、最终响应/状态。对有副作用的能力还需核对测试环境中的实际状态与重复执行风险。
- 用独立临时数据及可控测试依赖，不接触生产用户数据或执行未经授权的外部操作。测试失败须区分环境阻塞（额度、鉴权、网络等）、模型没有遵循明确指令、链路/能力实现错误。
- 模型输出具有随机性；显式指令用例不等同于确定性单元测试，也不得用 Mock 的成功冒充真实模型验证通过。

### 示例（尚未实现的任务工具，仅说明验收方法）

假设提供 create_task(title)：

- 底层：直接调用，断言任务真实写入；测试空标题、写入失败等边界。
- 模拟模型链路：返回指定 create_task 的结构化调用，断言真实执行、任务状态和工具结果回传。
- 真实模型链路：用户输入“请调用 create_task 工具，创建标题为‘阅读30分钟’的任务”。断言确实调用了 create_task、参数正确、任务写入测试数据库、执行结果回传且 Agent 返回了响应。只说“已经创建”不能算通过。

当前 Agent 尚无工具调用/Skill 加载机制。以上是新增能力时的验收契约，不代表已实现工具或对应运行测试。现有真实模型测试仍受额度限制。

## 2. 智能体效果测试：理解、选择与解决效果

目标：给定自然用户场景，不预先告知应使用的具体工具或 Skill；验证智能体能否理解需求，自主判断是否需要加载/调用能力、选择适当的能力与参数，最终解决问题并提供合理回答。

评估维度按场景选取：

- 用户意图及约束是否被正确理解；是否需要澄清。
- 是否在合适时机加载合适的 Skill、发现/选择合适的工具；是否避免无必要调用。
- 执行参数、顺序及协作是否合理；失败后是否能适当处理。
- 用户目标是否实际达成（能核对真实状态时必须核对，不依赖文字自报）。
- 最终回答是否准确、有针对性、尊重自主性，解决效果如何。

同一能力应设计需要使用、不应使用、信息不足、多个能力可选等不同场景。允许多条合理解决路径；除业务硬性约束外，不强制唯一工具序列。预期行为与评审标准只提供给评测端，不注入被测 Agent 的对话上下文。

### 同一工具的场景示例（假设未来实现任务工具）

| 自然用户输入 | 预期表现 |
| --- | --- |
| 帮我记一下，明天读30分钟书 | 理解明确记录请求，使用合适任务能力并确认实际创建 |
| 我最近想多读点书，但总坚持不下来 | 先理解障碍、给出合理帮助；不擅自创建任务 |
| 帮我把之前的阅读计划改一下 | 先定位计划，必要时澄清修改内容，再使用适当能力 |
| 我想增加阅读时间，又不想影响睡眠，你觉得怎么安排？ | 权衡约束，提供适合的建议；不把咨询直接当作创建任务指令 |

### 当前最小框架

当前只建立 evaluation/cases.json（场景、用户轮次、人工验收标准）和最小执行入口。三个案例仅供示例，不构成完整评测集。默认列出并校验用例，不调用真实模型：

    python -m evaluation

额度恢复后，明确选择一个案例并配置环境变量，再运行：

    python -m evaluation --live --case intent-001

每次使用独立内存数据库，按场景轮次调用实际 Agent，输出回复和人工审查标准。仅使用虚构内容；不自动打分、不宣称质量通过、不运行于 CI 的真实模型步骤中。暂不引入 LLM 裁判、基线对比、复杂评分、批量评测或长期用户模拟。

当前入口仅输出对话文本，尚不能记录工具/Skill 执行轨迹或核对任务状态；待实际能力及事件机制实现时再接入可观测轨迹和结果断言。不能用回复文本替代执行证据。后续按已实现能力逐步增加案例和评测方式，涉及模型随机性的质量结论需要实际多次运行及人工校准。

## 长期记忆真实对话质量诊断

新增 `evaluation.memory_quality`。与 cross_time 的预置记忆不同，它通过真实 Agent.reply 顺序处理虚构用户历史，在测试专用 SQLite 中给每轮记录设定 UTC 日期，实际进行提取、写入、修订和检索。最终从同一数据库快照独立比较无记忆、V1.1 语义检索与 V1.2 综合检索，关闭近期历史窗口以隔离长期记忆贡献。三组分别覆盖职业与价值观、否定及纠正、密集陈述与 44 条干扰记忆。质量诊断不会把期望原话、标签或审核标准提供给被测模型。

    python -m evaluation.memory_quality
    python -m evaluation.memory_quality --live --case quality-001 --output quality-001.json

默认只验证场景；真实调用必须显式启用并配置现有 BECOMING_* 环境变量。quality-003 有 46 轮历史，最多约 193 次模型调用（每轮最多四次，另三组探测最多八次），建议单独按额度运行。报告含逐轮对话、读写/错误事件、实际存储、来源、期望连续原话是否完整出现、修订状态、无预期写入轮次的审查标记、候选与最终选择的诊断及调用次数。候选追踪仅 V1.2 可用。完全匹配是保守的结构证据代理，不代表语义准确性或质量分数；可能漏算等价表达或跨轮合并，需人工检查实际存储、上下文和回答。未命中分为存储缺失、候选范围外、候选未选择；基线无候选轨迹时明确标记不可判定。不要把预置历史的探测或离线模拟冒充真实效果。

离线新增确定性测试：评测隔离、时间记录、证据诊断、原有单轮三条上限与无词法重叠的 40 候选上限。后两项是已知限制的可复现证据，不是待修复功能已通过验收。CI 仅验证离线测试及场景合法性，不自动消耗模型额度。现有主分支手动真实测试工作流安全限制保持不变；开发分支可在已配置模型的本地环境手动运行以上命令。

## 真实模型完整质量评测（V1）

新增 evaluation/live_quality.py，使用真实配置模型执行连续多轮虚构场景。当前评测分为：
- 人生意义探索、具体经历、用户纠正；另与仅保留基础角色提示词的对照组并排记录。
- 职业决策与明确现实约束。
- 综合长期记忆的提取、第三方/短暂情绪抑制、偏好修订、跨轮召回、历史回顾及无关主题过滤。该场景关闭近期历史窗口。
- 成长目标、行动、完成状态、复盘和查询；测试夹具只确认与预期工具及实际数据库 ID 匹配的合成提案。
- 倾听、不建议、话题切换及不创建成长记录。
- 即时安全风险响应（必须人工安全审查）。

默认命令仅列出并校验测试夹具，不访问模型。真实执行需显式设置 BECOMING_BASE_URL、BECOMING_API_KEY、BECOMING_MODEL 并传入 --live。默认总调用预算为 60 次，超过预算立即停止；不自动重试。报告不会记录 API Key 或请求头。成长提案中的确认 nonce 会在报告中脱敏。

报告包括逐轮真实回复、调用次数与耗时、记忆事件、候选/召回 ID、成长工具事件、合成确认结果及最终数据库状态。结构性断言用于发现存储、调用和状态问题；语义质量不自动评分。报告必须由人工逐轮审查，尤其是建议是否真正贴合用户、是否尊重自主权及安全响应是否充分。GitHub Actions 成功只代表评测执行完成，不代表产品质量验收通过。


## 动态个人理解 V1 新增验收

### 离线功能测试

`tests/test_personal_understanding.py` 覆盖：

- Evidence 原话必须来自对应 user_text；伪造引用、越权 Claim ID、过期版本和敏感/凭据候选拒绝。
- Claim 创建、REINFORCE、REFINE、DISPUTE、REJECT、确认与版本历史。
- 支持等级由程序计算；高支持等级需要跨日期的独立证据或用户明确确认。
- 重要纠正即时更新、普通轮次最多 5 条合批、有限重试。
- PendingConfirmation 只等待紧接着的下一轮用户回应；含糊回应和错过时机均过期。
- 检索上下文、无关话题过滤、反思类问题对 goals/constraints 的覆盖、Agent 可选集成及默认路径无额外模型调用。
- `/clear` 删除来源对话时，级联清除证据、无证据版本、命题、修订、待确认项和任务。

默认离线命令仍为：

    python -m unittest discover -s tests -v
    python -m evaluation.personal_understanding

### 真实模型显式集成

`tests/live_personal_understanding.py` 使用独立内存数据库和虚构内容，验证用户明确要求更新、明确纠正旧理解、真实 Claim 版本变化、证据来源完整以及最终自然召回。它不进入默认离线测试发现范围。

配置现有 `BECOMING_BASE_URL`、`BECOMING_API_KEY`、`BECOMING_MODEL` 后手动运行：

    python -m unittest discover -s tests -p 'live_personal_understanding.py' -v

### 30 轮纵向效果评测

`evaluation/personal_understanding.py` 使用 `evaluation/personal_understanding_cases.json` 的 30 轮虚构对话，按顺序运行动态理解组；最终综合问题使用零轮近期历史窗口，并与同样零轮近期历史、未启用 PersonalUnderstanding 的基线回答对照。期望理解和人工评审标准只进入报告，不会注入 Agent。

默认只校验夹具，不请求模型。显式运行：

    python -m evaluation.personal_understanding --live --max-calls 80 --output artifacts/personal-understanding-live.json

报告记录逐轮回复、更新/检索事件、Claim/Revision/证据来源、模型调用数和基线回答，不自动评分。真实模型输出必须人工审查，尤其是第三方/假设/短暂情绪过滤、用户纠正后的旧版本处理、反向证据保留、无关检索以及最终综合回答。单次运行不能证明稳定性。

动态个人理解当前为同步原型：普通证据积累到 5 条或 20 轮触发点时同步批处理；CLI 退出时会 flush。GUI/服务端若需要真正不阻塞回复，后续应将 `process_pending` 放入后台 worker，而不是把当前同步行为误认为异步调度。CI 仅运行离线测试和夹具校验，不消耗模型额度，也不代表真实模型效果通过。
